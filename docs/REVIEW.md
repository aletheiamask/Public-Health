## สรุปภาพรวม

| ด้าน | ก่อนทบทวน | หลังแก้ | หมายเหตุ |
|---|---|---|---|
| ความทันสมัย | ดี | ดีมาก | แนวทางหลัก (Go + SSR + htmx + Postgres) เหมาะกับงานและทีมเล็ก — ปรับรายละเอียดให้ใช้ของใหม่ใน Go และเลิกพึ่ง Node |
| ความปลอดภัย | พอใช้ | ดี | ขาดหลายเรื่องที่สำคัญ: สแกนไวรัส, CSP ที่ใช้ได้จริง, กฎหมายเก็บ log, backup กัน ransomware, การกัน IDOR เชิงโครงสร้าง |
| ประสิทธิภาพ | ดี | ดีมาก | มีจุดคอขวดซ่อนอยู่ (นับยอดอ่าน, รายงานรับทราบ, แคชหลาย instance) และเป้าหมายยังวัดไม่ได้ |
| ความเป็นไปได้ของแผน | ต้องระวัง | ดีขึ้น | ระยะเวลาเดิมแน่นเกิน, สองเอกสารมี roadmap ไม่ตรงกัน, ไม่มี staging |

**จุดแข็งที่คงไว้:** Modular monolith ไบนารีเดียว, SSR เป็นหลัก (เร็ว เข้าถึงง่าย), Scoped RBAC บนต้นไม้หน่วยงาน, River คิวบน Postgres (ไม่ต้องมี Redis), แกน Workflow กลาง, ทำ LINE/Provider ID/AI เป็น adapter

## 2. ความปลอดภัย

| # | ระดับ | ปัญหาที่พบ | แก้แล้วอย่างไร |
|---|---|---|---|
| S1 | 🔴 | **ไม่มีสแกนไวรัสไฟล์อัปโหลด** — ระบบเผยแพร่เอกสารให้ทั้งจังหวัดดาวน์โหลด เป็นช่องทางกระจายมัลแวร์ได้ | เพิ่ม **ClamAV** สแกนก่อนเปิดให้ดาวน์โหลด, ไม่รับ SVG/HTML, เข้ารหัสรูปใหม่ + ลบ EXIF/GPS |
| S2 | 🔴 | **ขัดกฎหมาย**: แผนเดิมบอก "ไม่เก็บ IP ผู้อ่าน" แต่ พ.ร.บ.คอมพิวเตอร์ฯ กำหนดให้ผู้ให้บริการเก็บข้อมูลจราจรคอมพิวเตอร์ ≥ 90 วัน | เก็บ access log 90 วันแบบจำกัดสิทธิ์ แยกจากระบบสถิติ (สถิติยังไม่เก็บตัวตน — สอดคล้อง PDPA) |
| S3 | 🔴 | **Backup ไม่กัน ransomware** (ภัยหลักของหน่วยงานสาธารณสุขไทย) — ถ้าเครื่องโดนเข้ารหัส backup ที่ต่อออนไลน์อยู่ก็โดนด้วย | กฎ **3-2-1-1**: มี 1 ชุดแบบแก้ไข/ลบไม่ได้หรือออฟไลน์, backup เข้ารหัส, ทดสอบกู้คืนทุกเดือน, กำหนด **RPO ≤ 15 นาที / RTO ≤ 4 ชม.** |
| S4 | 🔴 | CSP แบบ nonce **ใช้จริงไม่ได้** กับ Alpine.js รุ่นปกติ (ต้องใช้ `unsafe-eval`) | ใช้ **Alpine รุ่น CSP**, ปิด eval ของ htmx — ได้ CSP เข้มงวดจริง |
| S5 | 🔴 | กัน IDOR/ข้ามขอบเขตด้วย "วินัยของโปรแกรมเมอร์" อย่างเดียว — ลืมกรองที่เดียวข้อมูลรั่ว | repo ที่คืนหลายแถว **ต้องรับ `authz.Scope`** (ลืมแล้ว compile ไม่ผ่าน) + test อัตโนมัติยิงทุก route ด้วยผู้ใช้ต่างขอบเขต |
| S6 | 🟠 | ไฟล์ภายในอาจเปิดผ่าน URL ตรงของ storage ได้ | ไฟล์ภายในผ่าน handler ตรวจสิทธิ์หรือ URL ลงลายเซ็นอายุ 5 นาที; ไฟล์ผู้ใช้เสิร์ฟจากโดเมนย่อยแยก + `CSP: sandbox` |
| S7 | 🟠 | Session ไม่กำหนดรายละเอียด (fixation, อายุ) | cookie `__Host-`, เปลี่ยน session ID เมื่อล็อกอิน, หมดอายุเมื่อไม่ใช้ 30 นาที (หลังบ้าน), สั่งออกทุกอุปกรณ์ได้ |
| S8 | 🟠 | การกระทำเสี่ยง (มอบสิทธิ์, ลบ, ลงนาม) ทำได้ด้วย session เดิม | **Step-up**: ยืนยัน Passkey/OTP ซ้ำทุกครั้ง |
| S9 | 🟠 | ไม่มีป้องกัน supply chain | SBOM, สแกน image, ลงนาม image, Renovate, container non-root/read-only/distroless |
| S10 | 🟠 | Audit log "append-only" แต่ผู้ดูแล DB ยังแก้ได้โดยไม่มีใครรู้ | **hash chain** ตรวจการแก้ย้อนหลังได้, เก็บ ≥ 2 ปี, partition รายเดือน |
| S11 | 🟠 | ลงนามอิเล็กทรอนิกส์มีหลักฐานอ่อน | step-up ณ ขณะลงนาม, hash เอกสารเก็บใน audit chain, ประทับเวลา RFC 3161 ถ้าใช้ได้, เอกสารที่ลงนามแล้วแก้ไม่ได้ |
| S12 | 🟠 | ไม่มีบัญชีฉุกเฉิน — ถ้า Super Admin ทุกคนเข้าไม่ได้ ระบบไม่มีใครดูแล | บัญชี break-glass เก็บในซองปิดผนึก ใช้แล้วแจ้งเตือนทุกคน |
| S13 | 🟠 | PDPA กล่าวถึงแค่ประกาศ/คุกกี้ | ROPA, ระยะเก็บข้อมูลทุกตาราง + ลบอัตโนมัติ, เข้ารหัสฟิลด์อ่อนไหว, แผนแจ้งเหตุรั่ว 72 ชม., DPIA ก่อนใช้ AI |
| S14 | 🟢 | นโยบายรหัสผ่านแบบเก่า | ยาว ≥ 12, ไม่บังคับอักขระพิเศษ, ตรวจรหัสที่รั่ว (ตามแนว NIST 800-63B), ข้อความล็อกอินผิดเหมือนกันทุกกรณี |
| S15 | 🟢 | ไม่มีการทดสอบเจาะระบบ | **pentest ก่อนเปิดใช้ทุกระยะ** และทุกปี; WAF (Coraza + OWASP CRS) เป็นทางเลือก |

## 3. ประสิทธิภาพ

| # | ระดับ | ปัญหาที่พบ | แก้แล้วอย่างไร |
|---|---|---|---|
| P1 | 🔴 | **รายงาน "ใครยังไม่รับทราบ" คำนวณจากกฎกลุ่มเป้าหมายทุกครั้ง** — ช้า และผิดเมื่อมีคนย้ายหน่วยงานหลังข่าวออก | ตาราง **`post_recipients`** สร้างรายชื่อผู้รับ ณ เวลาเผยแพร่ → ถูกต้อง + query เป็น index scan |
| P2 | 🟠 | นับยอดอ่านด้วย UPDATE แถวเดียวทุกครั้ง → แถวร้อน DB ติดขัดตอนข่าวด่วน | รวมยอดในหน่วยความจำแล้ว flush ทุก 1 นาที ลง `page_views_daily` |
| P3 | 🟠 | แผนเดิมพึ่ง "Caddy cache" แต่ **Caddy ไม่มีแคชในตัว**; แคชในหน่วยความจำไม่ sync ถ้ามีหลาย instance | แคชในแอป + ล้างด้วย **Postgres LISTEN/NOTIFY** + `singleflight` + `stale-while-revalidate` |
| P4 | 🟠 | ย่อรูป (libvips/CGO) และสร้าง PDF (Chromium) อยู่ใกล้เว็บ — กิน RAM และทำให้เว็บช้า/ล่มตาม | แยก **worker image** (มี libvips) และ **Gotenberg container** จำกัดงานพร้อมกัน; เว็บ build แบบ CGO-free |
| P5 | 🟠 | เป้าหมายประสิทธิภาพวัดไม่ได้ชัด ไม่มี load test | กำหนดเป้า p95/LCP/INP/req/s ชัดเจน + **k6 load test** เป็นเกณฑ์ก่อนเปิดใช้ |
| P6 | 🟠 | สเปกเครื่องเดิม (16 GB) ไม่พอเมื่อเพิ่ม Meilisearch, ClamAV (~1–2 GB เอง), Gotenberg | **32 GB RAM, NVMe** |
| P7 | 🟢 | เว็บกับ worker แย่ง connection pool เดียวกัน | แยก pgxpool ต่อบทบาท |
| P8 | 🟢 | SSE หลายแท็บอาจติดเพดานการเชื่อมต่อ | SSE ผ่าน HTTP/2 + heartbeat |

## 5. ข้อแนะนำเพิ่มเติม (ยังไม่ได้ใส่ในแผน — รอตัดสินใจ)

1. **ทีมและผู้รับผิดชอบ** — ระบุคนดูแลระบบหลังเปิดใช้ (อย่างน้อย 1 คนที่ สสจ. รู้วิธี deploy/กู้คืน) และทำคู่มือ runbook; ถ้าจ้างภายนอก ให้ระบุในสัญญาว่าต้องส่งมอบซอร์สโค้ด + เอกสาร + การอบรม
2. **ทดสอบกับผู้ใช้จริงตั้งแต่ระยะ 0** — ใส่ไว้แล้ว แต่แนะนำเพิ่ม "ผู้ใช้ตัวแทน" ประจำ 5–8 คน (ผู้บริหาร, ธุรการ, เจ้าหน้าที่ รพ.สต., ผู้สูงวัย) ให้ทดลองทุกระยะ
3. **มาตรฐานที่ควรตรวจกับหน่วยงานกลางอีกครั้ง** — แนวปฏิบัติความมั่นคงปลอดภัยไซเบอร์ของ สธ./สกมช., มาตรฐานเว็บไซต์ภาครัฐ (สพร.), ระเบียบงานสารบรรณฉบับล่าสุด, ระเบียบการลา — เอกสารนี้อ้างอิงจากความรู้ทั่วไป ต้องยืนยันกับฉบับทางการก่อนใช้งานจริง
4. **ชื่อโดเมน** — ใช้ `.go.th` ของ สสจ.ตราด เพื่อความน่าเชื่อถือ (ประชาชนแยกเว็บจริง/ปลอมได้)
5. **ใช้ AI ระวังข้อมูล** — ถ้าเลือกใช้ ให้ทดลองเฉพาะเอกสารไม่อ่อนไหวก่อน (INTERNAL-SYSTEMS หัวข้อ 10)
